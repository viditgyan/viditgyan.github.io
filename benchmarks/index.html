Availability Formulas

Critical for Interviews
  • Availability = Uptime / (Uptime + Downtime)
  • Availability = MTBF / (MTBF + MTTR)
  • MTBF = Mean Time Between Failures
  • MTTR = Mean Time To Recovery
  • Series: A_total = A₁ × A₂ × A₃...
  • Parallel: A_total = 1 - (1-A₁)(1-A₂)...

Redundancy Impact

Example Calculations
  • Single server (99.9%): 8.77 hrs/year down
  • 2 servers parallel: 1 - (0.001)² = 99.9999%
  • 3 servers parallel: 1 - (0.001)³ = 99.9999999%
  • 2 in series (99.9% each): 99.8% total
  • Adding components in series reduces availability

Availability vs Durability
  • Availability: System is operational and accessible (can I access it now?)
  • Durability: Data is not lost (will my data survive failures?)
  • S3: 99.99% available but 99.999999999% durable (data survives even during outages)
  • High durability + low availability = data safe but temporarily inaccessible

Cache Hit Rate Target Aim for 95%+ cache hit rate for read-heavy workloads. Each cache miss typically costs 10-100× more than a cache hit. Monitor hit rate, eviction rate, and memory usage continuously.

Formulas:
  • Hit Rate = Cache Hits / (Cache Hits + Cache Misses) × 100%
  • Miss Rate = 1 - Hit Rate
  • Effective Latency = (Hit Rate × Cache Latency) + (Miss Rate × DB Latency)
  • Example: 95% hit rate, 1ms cache, 50ms DB → (0.95 × 1) + (0.05 × 50) = 3.45ms avg
  • Throughput Gain = 1 / (1 - Hit Rate × (1 - Cache Time/DB Time))

CDN Caching Strategy

  • Static assets: TTL 1 day - 1 year
  • API responses: TTL 1 sec - 5 min
  • Personalized content: No cache or vary headers
  • Versioned URLs: Long TTL (immutable)
  • Stale-while-revalidate: Reduce latency spikes

CDN Cost Model

  • Data transfer: $0.02-0.12/GB
  • Requests: $0.01 per 10K (varies)
  • Origin shield: Reduces origin hits
  • Reserved capacity: 20-40% savings
  • Egress to origin often free
CDN Hit Rate Formula
  • Hit Rate = Requests served from edge / Total requests × 100%
  • Origin Load = Total requests × (1 - Hit Rate)
  • Bandwidth Savings = Total bandwidth × Hit Rate
  • Example: 10M requests/day, 95% hit rate → Only 500K requests hit origin

📐 Capacity Estimation Examples

Twitter-like System (500M users)

Daily Active: 100M

  • Write TPS: 200M / 86400 ≈ 2,300 TPS
  • Reads/day: 100M × 100 reads = 10B
  • Read TPS: 10B / 86400 ≈ 115K TPS
  • Storage/year: 200M × 500B × 365 = 36TB

YouTube-like System (2B users)

Daily Active: 500M
  • Videos watched/day: 500M × 5 = 2.5B
  • Uploads/day: 500K videos
  • Storage/day: 500K × 100MB = 50TB
  • Bandwidth: 2.5B × 100MB / 86400 = 29 PB/day
  • CDN crucial: 29 PB = ~2.7 Tbps average

URL Shortener (100M URLs/month)

Read Heavy
  • Write TPS: 100M / 2.6M sec ≈ 40 TPS
  • Read:Write ratio: 100:1
  • Read TPS: 40 × 100 = 4,000 TPS
  • Storage: 100M × 500B = 50GB/month
  • 5 years: 50GB × 60 = 3TB

Chat System (50M users)

Real-time
  • Concurrent users (10%): 5M
  • Messages/user/day: 50
  • Total msgs/day: 50M × 50 = 2.5B
  • Peak TPS: 2.5B / 86400 × 3 = 87K
  • WebSocket connections: 5M concurrent
Estimation Formula Cheat Sheet
  • QPS: Daily requests ÷ 86,400 (multiply by 2-3× for peak)
  • Storage: Objects × Size × Retention × Replication factor
  • Bandwidth: QPS × Average response size
  • Servers: Peak QPS ÷ RPS per server (at 70% utilization)

Little's Law (Critical!)

Memorize This
  • L = λ × W
  • L = Average number of items in system
  • λ = Average arrival rate (requests/sec)
  • W = Average time in system (latency)
  • Example: 1000 RPS, 100ms latency → 100 concurrent requests
  • Use to size connection pools, thread pools, queues

Amdahl's Law

Parallelization Limits
  • Speedup = 1 / ((1-P) + P/N)
  • P = Parallelizable portion (0-1)
  • N = Number of processors
  • 90% parallel, 10 cores → 5.26× speedup (not 10×)
  • Serial portion limits maximum speedup
  • Applies to distributed systems too
Rule of 72 for Growth Time to double = 72 / Growth rate %. Example: 10% monthly growth → doubles in ~7 months. Plan capacity 6-12 months ahead for fast-growing systems.

Pareto Principle (80/20 Rule)

Data Distribution
  • Caching: 20% of data → 80% of reads
  • Users: 20% of users → 80% of traffic
  • Features: 20% of features → 80% of usage
  • Errors: 20% of bugs → 80% of crashes
  • Implication: Cache the hot 20% for massive gains
  • Formula: Cache size ≈ 20% of total data for ~80% hit rate

Zipf's Law (Power Law)

Access Patterns
  • Frequency ∝ 1/rank (most popular item accessed most)
  • Item #1: 2× more access than #2
  • Item #1: 10× more access than #10
  • Top 1% items: ~30% of traffic
  • Top 10% items: ~65% of traffic
  • Hot keys cause sharding challenges
Applying 80/20 in System Design
  • Cache sizing: Start with 20% of working set, monitor hit rate, adjust
  • Sharding: Hot keys (celebrities, viral content) need special handling
  • Read replicas: Most traffic is reads; scale reads separately
  • Optimization: Profile first, optimize the 20% causing 80% of latency

🌐 Overview

HTTP delivery patterns let producers and consumers stay in sync without forcing constant manual refresh. The right choice depends on latency goals, client reach, infrastructure maturity, compliance requirements, and operational constraints.

Core insight Match the transport to the business SLA. A trading desk demanding <50 ms updates, a collaboration app maintaining shared cursors, and a SaaS admin console showing aggregated metrics each favor different delivery semantics.

Latency target

Event freshness

Sub-second feedback loops (collaboration cursors, in-game telemetry) benefit from bidirectional protocols that keep connections warm (WebSockets, WebRTC, gRPC streaming).

Client footprint

Browser support

Browsers, mobile SDKs, IoT sensors, and server-to-server channels expose different transport support. SSE and WebSockets work natively in modern browsers; gRPC streaming typically sits inside service meshes.

Operational shape

Scaling strategy

Stateless fleets with L7 load balancers prefer long polling. Stateful connection brokers or dedicated gateways suit WebSockets, SSE, and HTTP/2 streaming.

Connection initiation in practice
  • Every option begins with a client-initiated handshake because browsers, NATs, and firewalls block unsolicited inbound sockets.
  • Once that session is open, push-capable channels (SSE, WebSockets, gRPC streaming, WebRTC) let the server publish updates without waiting for another request.
  • Pure polling (REST, long polling fallback) remains entirely client-driven, making it the resilience baseline when push mechanisms are unavailable.

🧭 Selection Heuristics

Pick REST polling when…

  • Requirements allow refresh latency measured in seconds or minutes.
  • Infrastructure favors stateless, auto-scaled HTTP endpoints behind CDNs.
  • You want simple API semantics that reuse existing REST/RESTful client libraries.

Pick long polling when…

  • Clients already operate behind strict proxies or corporate firewalls that block WebSockets.
  • Update cadences are predictable (every few seconds) and tolerance for stale data exists.
  • You need a fallback path for unreliable networks (e.g., Slack and Gmail use long polling fallbacks).

Pick WebSockets when…

  • Bi-directional, sub-second interactions matter (collaboration cursors, multiplayer state syncing).
  • Message frequency is high enough that HTTP request overhead dominates.
  • You can run stateful gateways or leverage managed brokers (AWS API Gateway WebSocket, Socket.IO hubs).

Pick SSE when…

  • Updates flow one way (dashboards, alerting, progress indicators).
  • You want HTTP semantics plus auto-reconnect/resume, without custom framing.
  • Messages are lightweight text or JSON payloads (CI pipeline events, GitHub Actions logs).

Pick HTTP/2 or gRPC streams when…

  • Service-to-service streaming is required with flow control and typed contracts.
  • You already operate service meshes supporting mTLS and HTTP/2 aware load balancers.
  • You need bi-directional streaming for ML inference or IoT command channels.

🧱 Standard REST Polling

The conventional request/response pattern issues periodic HTTP GETs against RESTful endpoints. Clients accept that data may be stale between polls, trading timeliness for implementation simplicity and broad compatibility with caches, CDNs, and dev tooling.

Advantages

  • Works anywhere plain HTTPS works: browsers, mobile SDKs, cron jobs, server-side scripts.
  • Stateless handlers scale horizontally and benefit from CDN edge caching and retries.
  • Easy to secure with OAuth/JWT, WAFs, and standard API gateways.

Limitations

  • Data freshness is bounded by poll interval; clients miss events between requests.
  • Repeated full payload transfers inflate bandwidth costs versus delta-based channels.
  • Under heavy fan-out, origin services may see thundering herds after cache expiry.

Production Use Cases

Status dashboards Scheduled syncs Public APIs

REST polling powers API-first SaaS integrations, cron-based data syncs, and dashboards that tolerate multi-second refresh cycles (e.g., marketing analytics, nightly ETL monitors). 

// Spring REST controller for periodic polling
@RestController
@RequestMapping("/api/metrics")
public class MetricsController {

    private final MetricsService metricsService;

    public MetricsController(MetricsService metricsService) {
        this.metricsService = metricsService;
    }

    @GetMapping
    public ResponseEntity<MetricsSnapshot> fetch(@RequestParam(defaultValue = "team") String scope) {
        MetricsSnapshot snapshot = metricsService.snapshot(scope);
        return ResponseEntity.ok()
            .cacheControl(CacheControl.maxAge(Duration.ofSeconds(15)))
            .body(snapshot);
    }
}
Implementation notes Publish `Cache-Control`/`ETag` headers so caches absorb redundant pulls, and add jitter to client polling intervals to avoid synchronization bursts when credentials or cache entries expire.

⏳ Long Polling

The client issues a request that the server holds open until new data arrives or a timeout occurs. The client immediately re-issues the request once it returns, enabling near-real-time updates with ordinary HTTP infrastructure.

Advantages

  • Works end-to-end through CDNs, WAFs, and enterprise proxies by reusing HTTP semantics.
  • No specialized gateway: horizontal scaling via stateless application tiers.
  • Straightforward observability (HTTP access logs, request-level metrics).

Limitations

  • Idle connections waste server threads if not coupled with async/reactive I/O.
  • Latency floor depends on poll timeout; bursty workloads can thrash connection pools.
  • Resource-heavy at massive scale (each client repeatedly negotiates HTTP headers).

Production Use Cases

Slack fallback Salesforce Streaming API (CometD) Legacy mobile push

Slack, Salesforce, and long-lived admin consoles rely on long polling as a compatibility layer when WebSockets are blocked or as a gradual migration path. 

// Spring Boot controller using DeferredResult for long polling
@RestController
@RequestMapping("/events")
public class LongPollingController {

    private final SubscriptionHub hub;

    public LongPollingController(SubscriptionHub hub) {
        this.hub = hub;
    }

    @GetMapping
    public DeferredResult<ResponseEntity<EventBatch>> next(@RequestParam String cursor) {
        DeferredResult<ResponseEntity<EventBatch>> result = new DeferredResult<>(30_000L);
        hub.register(cursor, result);
        result.onTimeout(() -> result.setResult(ResponseEntity.noContent().build()));
        result.onError(throwable -> hub.deregister(cursor));
        return result;
    }
}
Implementation notes Use async servlet processing (DeferredResult, WebFlux, Netty) to prevent thread exhaustion. Cache miss detection and delta compression (JSON patch, protocol buffers) cut payload size.

🔄 WebSockets

A single HTTP upgrade handshake establishes a persistent TCP connection with lightweight frames flowing in both directions. Ideal for high-frequency, interactive workloads.

Advantages

  • Bi-directional messaging with minimal framing overhead; supports binary payloads.
  • Back-pressure via flow control libraries (Netty, Jetty) helps protect upstream services.
  • Excellent for event fan-out through in-memory hubs or managed brokers (Ably, Pusher, Azure Web PubSub).

Limitations

  • Requires sticky sessions or connection brokers to maintain affinity.
  • Stateful connection management complicates autoscaling and blue/green deployments.
  • Some corporate proxies terminate idle sockets; heartbeat and reconnect logic is mandatory.

Production Use Cases

Figma multiplayer cursors Bloomberg FX feeds Uber driver dispatch

Design collaboration, trading dashboards, and ride-hailing apps rely on WebSockets to synchronize state with sub-second latency. 

// Simple WebSocket handler using Spring WebSocket
@Component
public class TickerSocketHandler extends TextWebSocketHandler {

    private final Set<WebSocketSession> sessions = ConcurrentHashMap.newKeySet();

    @Override
    public void afterConnectionEstablished(WebSocketSession session) {
        sessions.add(session);
    }

    @Override
    protected void handleTextMessage(WebSocketSession session, TextMessage message) throws Exception {
        for (WebSocketSession openSession : sessions) {
            if (openSession.isOpen()) {
                openSession.sendMessage(message);
            }
        }
    }

    @Override
    public void afterConnectionClosed(WebSocketSession session, CloseStatus status) {
        sessions.remove(session);
    }
}
Operational guardrails Terminate TLS at edge nodes that understand WebSocket upgrades, enforce idle timeouts (e.g., two minutes), and emit per-connection metrics (connected, dropped, upgrade failures) to capacity dashboards.

📣 Server-Sent Events (SSE)

SSE streams text-based events over long-lived HTTP responses. Browsers expose the EventSource API, automatically handling reconnects and last-event-id resumption.

Advantages

  • Auto-reconnect, heartbeat, and backoff handled by the browser EventSource.
  • Uses standard HTTP/1.1; easy observability and compatible with HTTP caching headers.
  • Ideal for status dashboards, CI/CD logs, GitHub notification feeds, Stripe webhook monitors.

Limitations

  • One-way only (server → client). Pair with fetch or WebSocket for upstream commands.
  • UTF-8 text payloads only; binary data must be base64 encoded.
  • Some enterprise proxies buffer responses—send periodic heartbeat comments (:keep-alive).

Production Use Cases

GitHub Actions log streaming Vercel build output Kubernetes dashboard events

Engineering teams lean on SSE to surface incremental progress without reloading pages or upgrading to WebSockets. 

// Spring MVC endpoint returning an SseEmitter
@RestController
public class DeploymentStreamController {

    private final DeploymentEventPublisher publisher;

    public DeploymentStreamController(DeploymentEventPublisher publisher) {
        this.publisher = publisher;
    }

    @GetMapping(path = "/stream/deployments", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    public SseEmitter streamDeployments() {
        SseEmitter emitter = new SseEmitter(0L); // never times out
        publisher.register(emitter);
        emitter.onCompletion(() -> publisher.deregister(emitter));
        emitter.onTimeout(() -> publisher.deregister(emitter));
        return emitter;
    }
}
Implementation notes Flush the response buffer after each event, emit comment heartbeats every 15–30 seconds, and cap outstanding emitters per node to avoid memory pressure.

🔗 HTTP/2 & gRPC Streaming

HTTP/2 enables multiplexed streams on a single TCP connection. gRPC builds on HTTP/2 to provide typed contracts, flow control, and client/server/bidirectional streaming primitives.

Advantages

  • Multiplex many logical streams per connection (fewer sockets, better for microservices).
  • Built-in back-pressure and flow control prevents overwhelming consumers.
  • Protobuf schemas give forward/backward compatibility and tooling for stubs.

Limitations

  • Browsers lack native gRPC streaming; use gRPC-Web with Envoy proxy for unary calls.
  • Edge load balancers must support HTTP/2 end-to-end to retain streaming benefits.
  • Extra effort to expose observability (per-stream metrics, message sizes) if not using service mesh.

Production Use Cases

Netflix control plane Stripe internal ledgers Cloud Spanner client

Internal service meshes rely on gRPC streaming for config propagation, ledger event propagation, and ML inference pipelines. 

// gRPC bidirectional stream in Java (io.grpc)
public class EventStreamService extends EventStreamGrpc.EventStreamImplBase {

    @Override
    public StreamObserver<ClientEvent> connect(StreamObserver<ServerEvent> responseObserver) {
        return new StreamObserver<>() {
            @Override
            public void onNext(ClientEvent request) {
                ServerEvent ack = ServerEvent.newBuilder()
                    .setCorrelationId(request.getCorrelationId())
                    .setStatus("ACK")
                    .build();
                responseObserver.onNext(ack);
            }

            @Override
            public void onError(Throwable t) {
                // log and cleanup resources
            }

            @Override
            public void onCompleted() {
                responseObserver.onCompleted();
            }
        };
    }
}
Implementation notes Prefer Envoy or Linkerd to terminate TLS and enforce retries. Enable message compression (gRPC supports gzip) and set max inbound message sizes to defend against abuse.

📡 WebRTC Data Channels

WebRTC establishes peer-to-peer channels optimized for low-latency delivery. Data channels reuse SCTP over DTLS, inheriting congestion control tuned for real-time media.

Where it shines

  • Browser-to-browser collaboration (Figma multiplayer, Miro cursors) with mesh topologies.
  • Live media applications (video conferencing, cloud gaming) requiring synchronized control data.
  • IoT gateways needing direct peer channels with fallback to TURN relays.

Operational considerations

  • Requires signaling service (often via WebSocket) for SDP/ICE exchange.
  • TURN servers add bandwidth cost but guarantee connectivity through restrictive NATs.
  • Observability is harder: rely on WebRTC stats API and tracing aggregated via RTCPeerConnection.
// Java signaling snippet using WebSocket to exchange WebRTC offers
@Component
public class SignalingSocketHandler extends TextWebSocketHandler {

    private final Map<String, WebSocketSession> peers = new ConcurrentHashMap<>();

    @Override
    public void afterConnectionEstablished(WebSocketSession session) {
        peers.put(session.getId(), session);
    }

    @Override
    protected void handleTextMessage(WebSocketSession session, TextMessage message) throws Exception {
        SignalingPayload payload = parse(message.getPayload());
        WebSocketSession target = peers.get(payload.targetId());
        if (target != null && target.isOpen()) {
            target.sendMessage(new TextMessage(message.getPayload()));
        }
    }

    @Override
    public void afterConnectionClosed(WebSocketSession session, CloseStatus status) {
        peers.remove(session.getId());
    }
}

Run TURN (Traversal Using Relays around NAT) servers in multiple regions to avoid asymmetrical routing. Monitor relay utilization to scale bandwidth ahead of peak events.

📮 Webhooks & Event Bridges

When clients do not maintain persistent connections, publish events to consumer-owned endpoints or managed event bridges. Pair with retries, signatures, and dead-letter queues for reliability.

Use cases

  • Third-party integrations (Stripe, Shopify, GitHub) pushing lifecycle events.
  • Internal decoupling across bounded contexts (billing → analytics).
  • Hybrid cloud fan-out via Amazon EventBridge, Google Eventarc, Azure Event Grid.

Hardening tips

  • Include HMAC signatures and timestamps to defend against replay attacks.
  • Idempotency keys prevent duplicate processing after retries.
  • Use exponential backoff with DLQs to handle persistent consumer failures.
// Spring webhook dispatcher with signature verification
@RestController
public class WebhookController {

    private final SignatureVerifier verifier;
    private final EventProcessor processor;

    public WebhookController(SignatureVerifier verifier, EventProcessor processor) {
        this.verifier = verifier;
        this.processor = processor;
    }

    @PostMapping("/webhooks/partner")
    public ResponseEntity<Void> receive(
        @RequestHeader("X-Signature") String signature,
        @RequestHeader("X-Timestamp") String timestamp,
        @RequestBody String payload
    ) {
        verifier.requireValid(signature, timestamp, payload);
        processor.enqueue(payload);
        return ResponseEntity.accepted().build();
    }
}
Fallback strategy Pair webhooks with a pollable status API so consumers can recover missed deliveries during outages or credential rotations.

🛠️ Capacity & Scaling

Connection management

  • Track concurrent connections per node and enforce quotas to avoid exhausting file descriptors.
  • Use connection brokers (NGINX, HAProxy, Envoy) with consistent hashing for WebSockets.
  • Warm standby nodes before scale-out to avoid connection storms.

Message delivery

  • Separate ingestion from fan-out using message brokers (Kafka, NATS, Redis Streams).
  • Batch/compress payloads (protobuf, JSON lines) to reduce bandwidth for chatty channels.
  • Apply QoS tiers (premium vs free) via weighted fair queues to control abuse.

Testing & chaos

  • Load test connection churn (connect/disconnect) in addition to steady-state throughput.
  • Simulate throttled cellular links to evaluate heartbeat and reconnect strategies.
  • Inject delayed or reordered messages to validate idempotency and ordering guarantees.

🛡️ Security & Compliance

Transport hardening

  • Terminate TLS 1.2+ with modern cipher suites (ECDHE+AES-GCM or ChaCha20-Poly1305).
  • Require WSS for WebSockets; enforce HSTS and strict origin checks.
  • For gRPC, prefer mTLS with SPIFFE identities to isolate workloads.

Authentication & authorization

  • Issue short-lived JWT or opaque tokens and validate them at connection upgrade.
  • Enforce channel-level authorization (rooms, topics) server side to stop spoofed subscriptions.
  • Throttle join/leave and message rates per identity to combat flooding attacks.
Auditability Emit connection audit logs (who connected, scopes, IPs) and message metadata (size, rate) to SIEM platforms. Retain replayable event logs for compliance investigations.

🧯 Troubleshooting Playbook

Symptom: High reconnect churn

  • Check idle timeout mismatch between client (heartbeat) and load balancer.
  • Inspect TLS termination for handshake failures (cipher mismatch).
  • Review DNS load balancing; sticky sessions may collapse onto a single node.

Symptom: Stale data

  • Ensure fan-out tier publishes to all shards (consistent hashing bugs can starve clients).
  • Measure end-to-end latency (ingest → broker → connection). Identify slow consumers via lag metrics.
  • Enable heartbeats and sequence IDs to detect dropouts quickly.

Symptom: Memory pressure

  • Bound per-connection buffers and apply back-pressure or drop oldest messages.
  • Instrument queue depth and publishing latency; set alerts before OOM occurs.
  • Use adaptive fan-out (delta updates) to reduce payload size for slow clients.

📋 Implementation Checklist

Before launch

  • Decide fallback paths (WebSockets → SSE → long polling) and test downgrade flow.
  • Provision capacity: estimate connections per node, message rate, and TLS handshake budget.
  • Document SLAs (latency, message ordering, durability) and align with stakeholders.

After launch

  • Monitor connection churn, message throughput, error rates, and reconnect loops.
  • Run load regression before major events (marketing campaigns, market open).
  • Review incident postmortems; tune backoff, buffer limits, and readiness probes.

1 Cache Locality Tuning

Arrange data structures and access patterns to maximize CPU cache hits. L1 cache access is ~1ns vs ~100ns for main memory — a 100x difference that compounds in hot loops.

CPU-bound Memory

Core Principles

  • Spatial locality: Access contiguous memory (arrays > linked lists)
  • Temporal locality: Reuse recently accessed data
  • Cache line size: 64 bytes on modern CPUs—align structs
  • False sharing: Separate frequently-modified fields to different cache lines

Real-World Usage

  • ClickHouse: Columnar (SoA) layout for SIMD-friendly scans
  • Redis: Flat structs for hot metadata paths
  • Game engines: ECS architecture, struct-of-arrays
  • HFT systems: Cache-line aligned order books
// Bad: Array of Structs (AoS) - poor cache utilization for column scans
struct User { long id; char name[64]; int age; double balance; };
User users[1000000];  // Scanning ages touches 80 bytes per user

// Good: Struct of Arrays (SoA) - cache-friendly for column operations
struct Users {
    long   ids[1000000];      // Contiguous IDs
    int    ages[1000000];     // Contiguous ages - 4 bytes per element
    double balances[1000000]; // Contiguous balances
};  // Scanning ages: 16 elements per cache line
When to Use: Hot loops, large dataset scans, compute-intensive paths, columnar analytics, real-time systems.
Avoid When: I/O-bound or network-bound workloads where cache optimization won't move the needle. Don't over-optimize cold paths.
🎯 Interview Signal: Explain the difference between AoS vs SoA with concrete numbers. Know L1/L2/L3 cache sizes (~32KB/256KB/8MB). Mention prefetching and false sharing.

2 Branch Prediction Awareness

Modern CPUs predict branches to keep pipelines full. Mispredictions cost 10-20 cycles. Avoid unpredictable branches in hot paths or make them branchless.

CPU-bound Latency

Techniques

  • Sort data: Make branches predictable
  • Branchless code: Use arithmetic instead of conditionals
  • Table lookups: Replace switch with arrays
  • CMOV instructions: Conditional moves avoid branches

Real-World Usage

  • Trading systems: Branchless order matching
  • Ad servers: Table-driven bid evaluation
  • Compression: Branchless Huffman decoding
  • Protocol parsers: State machines with jump tables
// Bad: Unpredictable branch in hot loop
for (int i = 0; i < n; i++) {
    if (data[i] >= 128)  // ~50% taken - worst case for predictor
        sum += data[i];
}

// Good: Branchless version
for (int i = 0; i < n; i++) {
    int mask = (data[i] - 128) >> 31;  // All 1s if < 128, all 0s otherwise
    sum += ~mask & data[i];           // Add only if >= 128
}

// Alternative: Sort first, then branch becomes predictable
Arrays.sort(data);  // Now branch is taken for latter half only
🎯 Interview Signal: Reference the famous Stack Overflow question about sorted array performance. Explain pipeline stalls. Know when NOT to use branchless code (readability vs nanoseconds trade-off).

3 Zero-Copy

Avoid copying data between kernel and user space, or between buffers. Critical for high-throughput systems where memory bandwidth is the bottleneck.

I/O Network Memory

Mechanisms

  • sendfile(): Direct file→socket transfer (Linux)
  • mmap: Map files directly into memory
  • splice/tee: Move data between pipes without copy
  • Direct I/O: Bypass page cache
  • RDMA: Direct memory access across network

Real-World Usage

  • Kafka: sendfile() for log segment transfer
  • Netty: CompositeBuffer, FileRegion
  • nginx: sendfile for static content
  • RocksDB: mmap for SST files
// Traditional copy (4 copies, 4 context switches)
read(file_fd, buffer, size);    // kernel→user copy
write(socket_fd, buffer, size); // user→kernel copy

// Zero-copy with sendfile (Linux) - 0 CPU copies
sendfile(socket_fd, file_fd, &offset, size);
// Data goes: disk → page cache → NIC (via DMA)
// CPU never touches the data!

// Java NIO zero-copy
FileChannel src = new FileInputStream(file).getChannel();
src.transferTo(0, src.size(), socketChannel);
When to Use: Large payload transfers (video streaming, log shipping), static file serving, high-bandwidth networking.
Avoid When: Data requires transformation (compression, encryption), small payloads where overhead isn't worth it, complex buffer management.

4 Lockless / Wait-Free Data Structures

Avoid mutex overhead using atomic operations (CAS, fetch-and-add). Critical for ultra-low-latency systems where lock contention dominates.

Concurrency Latency

Terminology

  • Lock-free: At least one thread makes progress
  • Wait-free: Every thread makes progress in bounded steps
  • Obstruction-free: Progress if run in isolation

Key Primitives

  • CAS (Compare-And-Swap)
  • FAA (Fetch-And-Add)
  • Memory barriers/fences

Real-World Usage

  • LMAX Disruptor: Lock-free ring buffer (6M+ msg/sec)
  • JVM ConcurrentLinkedQueue: Michael-Scott queue
  • HFT systems: Lock-free order books
  • Go runtime: Work-stealing queues
// Lock-free counter using CAS
public class LockFreeCounter {
    private final AtomicLong value = new AtomicLong(0);
    
    public long incrementAndGet() {
        long current, next;
        do {
            current = value.get();
            next = current + 1;
        } while (!value.compareAndSet(current, next)); // CAS loop
        return next;
    }
}

// Simpler: Use built-in atomic operations
AtomicLong counter = new AtomicLong();
counter.incrementAndGet();  // Uses hardware atomic instruction
⚠️ Complexity Warning: Lock-free code is notoriously hard to get right. Memory ordering, ABA problem, and testing are major challenges. Only use when contention is proven bottleneck.
🎯 Interview Signal: Explain the Disruptor pattern. Know ABA problem and solutions (tagged pointers, hazard pointers). Discuss memory ordering (acquire/release semantics).

5 Amortization

Spread expensive operations across many cheap ones. The occasional O(n) operation becomes O(1) amortized when it happens rarely enough.

Memory Latency

Classic Examples

  • ArrayList: Double capacity on resize (O(1) amortized add)
  • HashMap: Rehash when load factor exceeded
  • StringBuilder: Batch character appends
  • Generational GC: Minor collections are cheap

System-Level Amortization

  • Kafka: Batch commits to disk
  • LSM trees: Background compaction
  • Connection pools: Amortize connection setup
  • Buffer pools: Amortize allocation cost
// ArrayList amortized analysis
// Resize doubles capacity: 1→2→4→8→16...
// n insertions cause log(n) resizes
// Total copy cost: 1+2+4+...+n = 2n-1
// Amortized cost per insert: (2n-1)/n ≈ O(1)

// Kafka batch commit amortization
producer.send(record);  // Buffers in memory
// Actual disk write happens when:
// - Buffer full (batch.size)
// - Time elapsed (linger.ms)
// - Explicit flush()
⚠️ Tail Latency Risk: Amortization creates latency spikes. A HashMap rehash during a request can blow your p99. For strict SLAs, consider incremental approaches or pre-warming.

6 Lock Minimization

When you must use locks, minimize their scope, duration, and granularity. The goal: reduce contention without going fully lock-free.

Concurrency

Strategies

  • Lock striping: Partition data, one lock per partition (ConcurrentHashMap)
  • Read-write locks: Allow concurrent reads (ReentrantReadWriteLock)
  • Copy-on-write: Readers never block (CopyOnWriteArrayList)
  • Optimistic locking: Version checks instead of locks
  • Lock-free reads: Volatile + careful ordering

Scope Reduction

  • Hold locks for minimum time
  • Never do I/O while holding locks
  • Prepare data outside lock, update inside
  • Use ThreadLocal to avoid sharing
// Bad: Single lock for entire map
synchronized(map) { map.put(key, value); }

// Good: Lock striping (16 segments by default)
ConcurrentHashMap map = new ConcurrentHashMap<>();

// Better for read-heavy: Copy-on-write
CopyOnWriteArrayList items;  // Writes copy entire list

// Best for read-heavy with rare writes: Optimistic locking
do {
    version = data.getVersion();
    value = data.compute();
} while (!data.compareAndSetVersion(version, version + 1));
🎯 Interview Signal: Know when to use each strategy. ConcurrentHashMap internals (Java 7 segments vs Java 8 CAS + synchronized). Discuss lock ordering to prevent deadlocks.

7 Tail-Latency Awareness

At scale, p99/p999 matters more than average. If p99 is 100ms and you make 100 parallel calls, you'll likely see 100ms latency. Optimize the tail.

Latency Network

Tail Latency Amplification

  • Single 1% slow request → 100 deps → 63% chance of slowdown
  • Background tasks (GC, compaction) cause spikes
  • Queuing delays compound under load
  • Network hiccups affect subset of requests

Mitigation Strategies

  • Hedged requests: Send to multiple replicas, use first response
  • Tied requests: Send to two servers, cancel slower one
  • Timeouts: Aggressive timeouts + retry to different server
  • Circuit breakers: Fail fast when service degraded
// Hedged requests pattern
CompletableFuture primary = sendRequest(server1);
CompletableFuture hedged = primary
    .orTimeout(p95_latency, TimeUnit.MILLISECONDS)
    .exceptionally(ex -> {
        return sendRequest(server2).join();  // Hedge after p95
    });

// Google's approach: Send to 2 replicas immediately if request is "long"
// Cancel the slower one when first responds
// Reduces p99 latency significantly with minimal overhead
🎯 Interview Signal: Reference "The Tail at Scale" paper (Google). Know the math: P(at least one slow) = 1 - (1-p)^n. Discuss when hedging helps vs when it adds load.

8 Batching

Process multiple items together to amortize per-operation overhead. Fundamental trade-off: throughput increases, latency may increase.

I/O Network

Where Batching Wins

  • Disk I/O: Sequential writes >>> random writes
  • Network: Amortize TCP overhead, reduce RTTs
  • Database: Batch inserts 10-100x faster
  • RPC: Reduce serialization/network overhead

Real-World Examples

  • Kafka: batch.size + linger.ms
  • JDBC: addBatch() + executeBatch()
  • gRPC: Streaming RPCs
  • Redis: MGET, Pipeline
// Bad: Individual inserts (1000 round trips)
for (User u : users) {
    stmt.executeUpdate("INSERT INTO users VALUES (...)");
}

// Good: Batch inserts (1 round trip)
for (User u : users) {
    stmt.addBatch("INSERT INTO users VALUES (...)");
}
stmt.executeBatch();

// Kafka producer batching config
props.put("batch.size", 16384);     // Max bytes per batch
props.put("linger.ms", 5);           // Wait up to 5ms to fill batch
⚠️ Latency Trade-off: Batching adds latency (wait for batch to fill). Tune batch size and linger time based on your latency SLOs.

9 Asynchronous & Non-Blocking I/O

Don't block threads waiting for I/O. A single thread can handle thousands of connections with non-blocking I/O (epoll/kqueue/io_uring).

I/O Concurrency

Key Concepts

  • Event loop: Single thread polls for ready I/O
  • Reactor pattern: Demultiplex events to handlers
  • epoll (Linux): O(1) event notification
  • io_uring: True async I/O (Linux 5.1+)

Real-World Usage

  • Netty: EventLoop + ChannelPipeline
  • Node.js: libuv event loop
  • nginx: Worker processes with epoll
  • Redis: Single-threaded event loop
// Blocking I/O (1 thread per connection - doesn't scale)
while (true) {
    Socket client = server.accept();  // Blocks
    new Thread(() -> handle(client)).start();  // Thread per connection
}

// Non-blocking I/O with NIO Selector (thousands of connections per thread)
Selector selector = Selector.open();
serverChannel.register(selector, SelectionKey.OP_ACCEPT);

while (true) {
    selector.select();  // Wait for events (epoll under the hood)
    for (SelectionKey key : selector.selectedKeys()) {
        if (key.isAcceptable()) handleAccept(key);
        if (key.isReadable()) handleRead(key);
    }
}
🎯 Interview Signal: Explain C10K problem and how event-driven architecture solves it. Compare thread-per-request vs event loop models. Know the trade-offs (CPU-bound work still needs threads).

10 Backpressure

Slow down producers when consumers can't keep up. Prevents OOMs, queue explosions, and cascading failures.

Concurrency Network

Backpressure Mechanisms

  • Bounded queues: Block/reject when full
  • Credit-based: Consumer grants credits to producer
  • Rate limiting: Cap producer rate
  • TCP flow control: Window-based (built-in)

Real-World Usage

  • Reactive Streams: Publisher.subscribe with demand
  • Kafka: max.block.ms, buffer.memory
  • gRPC: Flow control windows
  • Akka Streams: Async boundaries with buffers
// Reactive Streams backpressure
Flux.range(1, 1000000)
    .onBackpressureBuffer(1000)  // Buffer up to 1000
    .subscribe(
        item -> process(item),     // Slow consumer
        error -> handleError(error),
        () -> complete()
    );

// Bounded BlockingQueue with backpressure
BlockingQueue queue = new ArrayBlockingQueue<>(1000);
// Producer blocks when queue full:
queue.put(task);  // Blocks if queue.size() == 1000
Without Backpressure: Unbounded queues → OOM. Dropping messages without acknowledgment → data loss. Fast producer overwhelms slow consumer → cascading failure.

11 Workload Shaping / Load Shedding

When overloaded, drop or degrade non-critical work to protect core functionality. Controlled degradation beats uncontrolled failure.

Latency Network

Strategies

  • Priority queues: Process high-priority first
  • Rate limiting: Cap requests per client/endpoint
  • Circuit breakers: Fail fast to degraded services
  • Graceful degradation: Return cached/stale data
  • Request deadlines: Drop requests past SLO

Real-World Usage

  • AWS: Throttling with exponential backoff
  • Google: CoDel (Controlled Delay) queues
  • Netflix: Hystrix circuit breakers
  • Envoy: Adaptive load balancing
// Load shedding with request deadlines
public Response handleRequest(Request req) {
    if (req.getDeadline().isBefore(Instant.now())) {
        metrics.increment("requests.shed");
        return Response.status(503).build();  // Don't waste work
    }
    // Process normally...
}

// Adaptive load shedding based on queue depth
if (queue.size() > HIGH_WATER_MARK) {
    if (req.getPriority() < CRITICAL) {
        return Response.status(503).build();  // Shed low-priority
    }
}

12 NUMA Awareness

On multi-socket systems, memory access is non-uniform. Local memory access is 2-3x faster than remote. Pin threads to NUMA nodes for consistent performance.

CPU Memory

NUMA Concepts

  • NUMA node: CPU socket + local memory
  • Local access: ~100ns
  • Remote access: ~200-300ns (QPI/UPI hop)
  • NUMA balancing: Linux auto-migration (imperfect)

Optimization Strategies

  • numactl: Pin processes to NUMA nodes
  • Interleave: Spread allocations for bandwidth
  • First-touch: Allocate on thread that first accesses
  • Huge pages: Reduce TLB misses
# Check NUMA topology
$ numactl --hardware

# Pin JVM to NUMA node 0
$ numactl --cpunodebind=0 --membind=0 java -jar app.jar

# Interleave memory across all nodes (good for bandwidth)
$ numactl --interleave=all java -jar analytics.jar

# JVM NUMA-aware GC (G1)
-XX:+UseG1GC -XX:+UseNUMA
🎯 Interview Signal: Know when NUMA matters (databases, in-memory systems, large heap JVMs). Explain first-touch policy. Mention that cloud VMs often abstract this away.

13 Memory Pooling / Object Reuse

Pre-allocate objects and reuse them to avoid allocation overhead and GC pressure. Critical for latency-sensitive applications.

Memory Latency

Pooling Patterns

  • Object pools: Reuse expensive objects (connections, buffers)
  • Arena allocation: Bulk allocate, bulk free
  • ThreadLocal caches: Per-thread pools (no contention)
  • Slab allocation: Fixed-size object pools

Real-World Usage

  • Netty: PooledByteBufAllocator
  • HikariCP: Connection pooling
  • Protocol Buffers: Arena allocation
  • Game engines: Entity pools
// Simple object pool
public class ByteBufferPool {
    private final Queue pool = new ConcurrentLinkedQueue<>();
    private final int bufferSize;
    
    public ByteBuffer acquire() {
        ByteBuffer buf = pool.poll();
        return buf != null ? buf.clear() : ByteBuffer.allocate(bufferSize);
    }
    
    public void release(ByteBuffer buf) {
        pool.offer(buf);  // Return to pool for reuse
    }
}

// Netty's pooled allocator (production-grade)
ByteBufAllocator alloc = PooledByteBufAllocator.DEFAULT;
ByteBuf buf = alloc.buffer(1024);
// ... use buffer ...
buf.release();  // Returns to pool
⚠️ Risks: Memory leaks (forget to release), use-after-free bugs, complexity. Pool sizing is tricky—too small causes allocation, too large wastes memory.

14 Profile-Guided Optimization (PGO)

Use production traffic profiles to guide compiler optimizations. The compiler inlines hot paths, optimizes branch layouts, and improves code locality.

CPU

How PGO Works

  • Instrument: Build with profiling enabled
  • Profile: Run with representative workload
  • Optimize: Rebuild using profile data
  • Typical gains: 10-30% performance improvement

JVM Equivalent

  • JIT compilation: Runtime profiling + optimization
  • Tiered compilation: C1 profiles → C2 optimizes
  • Warm-up: JVM needs traffic to optimize
  • AOT (GraalVM): Profile-guided native compilation
# C++ PGO workflow (clang)
# Step 1: Instrumented build
$ clang++ -fprofile-instr-generate -o app_instrumented app.cpp

# Step 2: Run with representative workload
$ ./app_instrumented < production_workload.txt
$ llvm-profdata merge -output=app.profdata default.profraw

# Step 3: Optimized build
$ clang++ -fprofile-instr-use=app.profdata -o app_optimized app.cpp

# Go PGO (Go 1.21+)
$ go build -pgo=auto  # Uses default.pgo if present

15 Data-Oriented Design

Design systems around data flow and transformation, not object hierarchies. Optimize for how data is accessed, not how it's conceptually organized.

Memory CPU

Principles

  • Understand the data: Size, access patterns, hot/cold
  • Separate hot from cold: Don't pollute cache with unused data
  • Batch similar operations: Better instruction cache
  • Avoid pointer chasing: Arrays > linked structures

Real-World Usage

  • Game engines: ECS (Entity Component System)
  • Databases: Columnar storage, vectorized execution
  • ML frameworks: Tensor operations on contiguous memory
// OOP: Objects with mixed hot/cold data
class Entity {
    int id;              // Hot: accessed every frame
    Vec3 position;       // Hot: updated every frame
    Vec3 velocity;       // Hot: updated every frame
    String name;         // Cold: rarely accessed
    Texture texture;     // Cold: only for rendering
    AudioClip sound;     // Cold: rarely accessed
}

// DOD: Separate hot and cold data
class Entities {
    // Hot arrays - updated every frame, cache-friendly
    int[] ids;
    Vec3[] positions;
    Vec3[] velocities;
    
    // Cold data - accessed rarely, separate cache lines
    Map metadata;
}
🎯 Interview Signal: Explain hot/cold data separation. Know ECS architecture. Discuss trade-offs: DOD can hurt code readability and OOP abstractions.

🔧 Language-Specific Considerations

Java / JVM

  • GC tuning: G1, ZGC for low latency
  • JIT warm-up: Critical for consistent latency
  • Off-heap: ByteBuffer.allocateDirect() avoids GC
  • Escape analysis: Stack allocation optimization
  • Tools: async-profiler, JFR, JMH for benchmarks

Go

  • GC: Low-latency by default, tune GOGC
  • Goroutines: Cheap, but still have overhead
  • sync.Pool: Built-in object pooling
  • Escape analysis: Use -gcflags="-m" to check
  • Tools: pprof, trace, benchstat

C++

  • No GC: Full control, full responsibility
  • RAII: Deterministic resource management
  • Move semantics: Avoid copies
  • Custom allocators: Arena, pool, slab
  • Tools: perf, VTune, Valgrind, sanitizers

Rust

  • No GC: Ownership model, no runtime cost
  • Zero-cost abstractions: High-level code, low-level perf
  • Unsafe: For when you need raw pointers
  • async/await: Zero-cost async
  • Tools: cargo flamegraph, criterion

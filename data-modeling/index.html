📐 Modeling Foundations

Data modeling is about representing business concepts, relationships, and lifecycle rules. Decisions you make early influence performance, consistency, and maintainability.

Start with Requirements

  • Gather access patterns (queries, lookup keys, aggregations).
  • Define SLAs (latency, throughput, consistency).
  • Capture lifecycle: creation, updates, retention, archival.

Business Vocabulary

  • Create conceptual model (entities, relationships, strong/weak dependencies).
  • Document attributes, data types, default values.
  • Align with domain-driven design (bounded contexts).

Balance Trade-offs

  • Normalisation vs denormalisation (write vs read heavy).
  • Consistency vs availability (CAP theorem, PACELC).
  • Storage cost vs query efficiency.

Documentation & Governance

  • Use ER diagrams, data dictionaries.
  • Establish naming conventions and standards.
  • Track data lineage and PII classification.

🗂️ Relational Modeling Patterns

Relational databases excel at structured data, strong consistency, and complex relationships.

Normalization (1NF–BCNF)

OLTP
  • Reduce redundancy, prevent update anomalies.
  • Use BCNF for transactional workloads; relax for read-heavy systems.
  • Document surrogate keys vs natural keys.

Denormalization

Read Optimized
  • Store computed/aggregated fields for fast reads.
  • Recalculate via triggers, jobs, or event sourcing.
  • Add documentation for derivation logic and refresh cadence.

Join Tables / Association

Relationships
  • Many-to-many via link tables (with extra attributes if needed).
  • Use cascades or application logic for referential integrity.
  • Index foreign keys and join columns.

Versioning & Temporal Tables

Auditing
  • Use Slowly Changing Dimensions (Type 2) or history tables.
  • Temporal tables in SQL Server/PostgreSQL (system versioning).
  • Track effective dates, validity windows.

Partitioning

Scale
  • Range/hash partition tables for large datasets.
  • Align indexes with partition keys.
  • Use partition pruning to speed queries.

Constraints & Integrity

Correctness
  • Set foreign keys, unique constraints, check constraints.
  • Use database migrations and CI checks to enforce rules.
  • Implement soft deletes carefully (status flags + filtered indexes).

🌲 NoSQL Data Patterns

NoSQL databases optimise for specific access patterns at scale. Model data around queries and consistency needs.

Key-Value

Cache/Session
  • Simple key → value lookups (Redis, DynamoDB).
  • Model per-key JSON blobs for quick retrieval.
  • Combine with TTL, version, or locking if needed.

Document Stores

Flexible Schema
  • Store JSON documents (MongoDB, Couchbase, Firestore).
  • Embed vs reference: embed for tightly coupled data, reference for shared data.
  • Precompute indexes and use schema validation when possible.

Wide-Column

Time-series/IoT
  • Partition key + clustering columns (Cassandra, HBase).
  • Design tables per query (query-driven modeling).
  • Plan TTLs, cold storage, and repair windows.

Graph

Relationships
  • Nodes, edges, properties (Neo4j, JanusGraph).
  • Use for highly connected data: social graphs, recommendations.
  • Model traversal patterns; index starting nodes.

Search Engine

Full-text
  • Index documents with tokenisation (Elasticsearch, Solr).
  • Design analyzers, shards, replicas based on query mix.
  • Keep source of truth elsewhere; use pipelines to sync.

Event Sourcing

Append-only
  • Store every change as an event; rebuild state with projections.
  • Ensure idempotent event handlers; manage schema evolution in events.
  • Use snapshots to accelerate rebuilds.

🔄 Hybrid & Polyglot Strategies

Most systems blend multiple models; ensure coordination and clarity on sources of truth.

Polyglot Persistence

  • Divide data domains across best-fit stores.
  • Maintain metadata catalog of data locations and owners.
  • Implement CDC to keep derived stores updated.

Read Models vs Write Models

CQRS
  • Command model handles writes with validation.
  • Query model built for fast reads (denormalized, aggregated).
  • Synchronise via events, message queues.

Federated GraphQL

  • GraphQL schema combined from multiple microservices.
  • Define resolvers pulling data from underlying stores.
  • Implement data loaders/batching to avoid N+1 issues.

Data Lakehouse

Analytics
  • Combine data lake storage (Parquet, ORC) with warehouse capabilities.
  • Table formats: Delta Lake, Apache Iceberg, Apache Hudi.
  • Support ACID transactions, schema evolution, time travel.

📊 Analytics & Warehouse Modeling

Analytical models optimise for aggregations, historical queries, and BI workloads.

Star Schema

Fact & Dimension
  • Central fact table with quantitative metrics.
  • Dimension tables describe entities (date, customer, product).
  • Use surrogate keys, hierarchical dimensions (snowflake as needed).

Data Vault

Flexibility
  • Hub (keys), link (relationships), satellite (attributes).
  • Supports agile data warehouses, auditable history.
  • Build star schemas as data marts on top.

Columnar Storage

High Compression
  • Store columns separately (Parquet, ORC, columnar DBs).
  • Enable predicate pushdown, vectorized execution.
  • Partition data by time, entity, or region.

Slowly Changing Dimensions

  • Type 1: overwrite (no history).
  • Type 2: add new row with effective dates.
  • Type 3: add new column for previous value.

Lakehouse Governance

  • Catalog (Glue, Hive Metastore, Unity Catalog) for schema tracking.
  • Data quality rules (Great Expectations, dbt tests).
  • Security: row/column masking, PII redaction, IAM.

Real-time Analytics

  • Streaming ETL (Kafka, Flink, Spark Structured Streaming).
  • Materialized views, incremental processing (ClickHouse, Materialize).
  • Handle late-arriving data via watermarks and windowing.

♻️ Schema Evolution & Data Governance

Data models must evolve without breaking downstream systems.

Versioning

  • Use backward-compatible schema changes when possible (add columns, default values).
  • Annotate schema migrations with release notes.
  • For event schemas, use Avro/Proto schema registry with compatibility checks.

Data Contracts

  • Define contracts between producers and consumers (API-like for data).
  • Automate validations (Great Expectations, Deequ) in CI pipelines.
  • Notify consumers before breaking changes.

Migration Strategies

  • Blue/green data migrations (dual write/read, switch after validation).
  • Shadow writes: write to new schema, compare results before cutover.
  • Backfill processes with monitoring & checkpoints.

Data Quality & Lineage

  • Set expectations for nullability, uniqueness, ranges.
  • Track lineage across pipelines (OpenLineage, DataHub, Amundsen).
  • Alert on out-of-spec data and escalate to data owners.

Use Case Modeling Approach Pros Considerations
Transactional system (OLTP) Normalised relational schema Strong consistency, ACID, avoids anomalies Potential joins, denormalize selectively for hot reads
Read-heavy API (profiles, catalogs) Denormalized tables + cache Fast reads, simpler queries Need mechanisms to keep data in sync
Time-series telemetry Wide-column store / time-series DB Efficient writes, TTL, rollups Use partition keys wisely, handle retention policies
Recommendation graph Graph DB Natural traversal, flexible relationships Different indexing, requires graph query expertise
Enterprise data warehouse Star schema / data vault Consistent analytics, slow-changing dimensions ETL/ELT pipelines, governance required
Event-driven system Event sourcing + CQRS Audit trail, rebuild state, async projections Complexity in projections, eventually consistent reads
Effective data models evolve with the business—iterate, measure impact, and keep stakeholders aligned on schema changes.

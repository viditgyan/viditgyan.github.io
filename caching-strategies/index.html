🧠 Caching Fundamentals

Caching reduces latency and offloads pressure from primary data stores, but introduces staleness and invalidation challenges. Choose caching explicitly—avoid accidental caches (HTTP proxies, ORM internal caches) without monitoring.

Key Concepts

  • Hit ratio: Hits ÷ (Hits + Misses). Track by resource and client type.
  • Latency per tier: Warm caches should reduce P95 by 50%+ relative to origin.
  • Cost awareness: Compare cache infra vs origin load savings.

When to Cache

  • Expensive or rate-limited operations (DB queries, API calls, compute-heavy rendering).
  • Frequently accessed, infrequently changing resources.
  • Hotspot traffic (popular product catalog, trending articles).

When Not to Cache

  • Highly dynamic or personalised content where stale data harms UX.
  • Data size exceeds cache budget or fetch cost is already small.
  • Complex invalidation logic outweighs performance benefit.

Metrics to Monitor

  • Hit/miss ratio, eviction counts, TTL expirations.
  • Cache latency vs origin latency, origin request rate.
  • Error/failure rates (timeouts, backend fallbacks).

🧩 Caching Patterns

Different workloads call for different caching approaches; pick patterns that align with data freshness, cost, and architecture.

Cache-aside (Lazy Loading)

Application Layer
  • App checks cache first → on miss fetches from origin → stores value.
  • Best when app controls lifecycle and misses are acceptable.
  • Beware: Stampede on cold start; add request coalescing.

Read-through / Write-through

Transparent Access
  • Cache provider fetches origin on miss automatically.
  • Write-through: writes go to cache and origin synchronously.
  • Suitable when using managed caches (e.g., AWS ElastiCache with Redis modules) or custom proxies.

Write-back (Write-behind)

High Throughput
  • Writes go to cache, asynchronously persisted to origin.
  • Boosts write throughput but risk of data loss on failure.
  • Use when durability handled via WAL/replication (e.g., CDN edge log shipping).

Global CDN Edge Cache

Web
  • Serves static assets, APIs with proper cache headers.
  • Combine with origin shielding, per-country rules.
  • Monitor cache keys, TTL, and invalidations closely.

Client-side Caching

Browser
  • Use HTTP caching headers (Cache-Control, ETag) effectively.
  • Service workers for offline-first experiences.
  • LocalStorage/IndexedDB for prefetching and reducing network calls.

Near-cache / Multi-layer

Microservices
  • Combine local in-process caches with shared caches (Redis).
  • Add stale-while-revalidate strategies to hide latency.
  • Use consistent hashing to distribute cache keys across nodes.

🧹 Eviction, Invalidation & Risk Mitigation

The hardest part of caching is keeping it correct and resilient. Choose eviction policies wisely and guard against common failure modes that can overwhelm origin systems.

Eviction Policies

  • LRU: Least Recently Used—great default for general workloads.
  • LFU: Keeps frequently accessed items (Redis LFU, Guava).
  • TTL-based: Expire after fixed time (cache-aside + TTL).
  • Random sampling: Scales for very large caches (e.g., Redis approximated LRU).

Invalidation Patterns

  • Explicit delete: Application removes cache after writes (cache-aside).
  • Versioned keys: Embed version/timestamp in key, rotate on release.
  • Event-driven: Use message queues or CDC to invalidate caches.

Cache Stampede

Traffic Spike
  • Multiple requests concurrently regenerate the same key when it expires.
  • Mitigation: Request coalescing, locks/mutexes, serve-stale-while-revalidate.
  • Add jitter to TTLs; pre-warm critical keys on deploy.

Cache Avalanche

Mass Expiration
  • Large number of keys expire simultaneously causing origin overload.
  • Mitigation: Randomize TTLs, stagger invalidations, partition cache clears.
  • Maintain origin capacity headroom; consider soft TTL + background refresh.

Cache Penetration

Miss Storm
  • Requests for non-existent keys always miss (malicious or flawed input).
  • Mitigation: Cache negative results briefly, validate inputs, use bloom filters.
  • Apply rate limiting / circuit breakers for suspicious patterns.

Cache Poisoning

Integrity Risk
  • Attackers or buggy services populate cache with incorrect data that then spreads quickly.
  • Impact: Users receive tampered responses, security controls bypassed.
  • Mitigation: Authenticate/authorise writes, validate payloads, use signed cache entries or E2E encryption.

Large Keys / Values

Memory & Network
  • Oversized keys or values increase serialization time, network transfer, and memory fragmentation.
  • Impact: Higher latency, eviction of useful data, cache node instability.
  • Mitigation: Use hashed/normalized keys, compress values, split blobs across tiers, enforce size limits.

Hot Keys / Hot Partitions

Load Imbalance
  • A small set of keys receives disproportional traffic, overwhelming specific nodes.
  • Impact: Increased latency, throttling, node failures, uneven eviction.
  • Mitigation: Key sharding (random suffixes), request replication, consistent hashing with virtual nodes, replicate popular keys.

Cache Coherence

Staleness
  • Multi-level or multi-region caches drift apart; clients see conflicting values.
  • Impact: Data inconsistency, violated invariants, user confusion.
  • Mitigation: Publish invalidations via pub/sub, use version tokens, employ write-through or lease-based protocols.

TTL & Refresh Strategies

  • Align TTL with data volatility and tolerance for staleness.
  • Use sliding TTL or refresh-ahead for frequently accessed keys.
  • Monitor near-expiry hits to detect aggressive TTL settings.
Action Items: instrument cache hit/miss metrics, track stampede events, and bake mitigation techniques (locks, jitter, negative caching) into library helpers or middleware so every team benefits.

🌍 Topology & Placement

Where you place caches influences latency, consistency, and operational complexity.

Client-side

  • Browsers, mobile apps, IoT devices.
  • Use HTTP caching headers, service workers, offline storage.
  • Consider: Security (no sensitive data), storage limits, versioning.

Edge/CDN

  • Global POPs, serverless edges (Cloudflare Workers, AWS CloudFront).
  • Cache static assets, API responses with proper TTL/invalidation.
  • Monitor regional hit ratios, shield origins for cascade protection.

Service/Proxy Layer

  • Reverse proxies (Varnish, Nginx), API gateways.
  • Shared caching across services (Redis, Memcached, Aerospike).
  • Implement authentication, TTL, and invalidation centrally.

In-process

  • Local caches (Guava, Caffeine, Spring Cache).
  • Minimal latency but requires keeping in sync with shared caches.
  • Add metrics to detect stale data and invalidation failures.

🔁 Consistency & Freshness

Caching inevitably introduces staleness; manage expectations and choose strategies based on tolerance for outdated data.

Strong vs Eventual

  • Strong: Writes immediately visible (write-through, read-after-write).
  • Eventual: Accept small window of stale data (cache-aside with TTL).
  • Clearly document which endpoints or data sets are eventual.

Stale-While-Revalidate

  • Serve cached content while refreshing asynchronously.
  • HTTP stale-while-revalidate directive or manual implementations.
  • Prevents stampede, keeps user latency low.

Write Propagation

  • Use pub/sub (Redis channel, Kafka) to broadcast invalidations.
  • Leverage change data capture (Debezium) to update caches.
  • Design fallback logic: on cache failure, degrade gracefully to origin.

Cache Coherency

  • Coordinate caches across regions with replication and versioning.
  • Track refresh timestamps in payload for debugging.
  • Consider write leases or compare-and-swap to prevent race conditions.

📊 Observability & Tuning

Monitor caches like production services—visibility ensures ROI and prevents hidden incidents.

Metrics

  • Hit ratio per resource/tenant, miss latency, backend fallbacks.
  • Evictions, expirations, memory usage, fragmentation.
  • Origin load reduction, cost savings estimates.

Logging & Tracing

  • Include cache metadata in traces (hit, miss, TTL left).
  • Log key invalidations, purge events, error responses.
  • Use sampling to avoid log volume explosion on high-QPS caches.

Testing Strategies

  • A/B test TTL changes to observe impact on latency and staleness complaints.
  • Load test with cold and warm scenarios.
  • Chaos experiments: simulate cache outages, forced evictions.

Cost Controls

  • Estimate break-even point (cache cost vs origin cost saved).
  • Set eviction and TTL policies to minimise oversized caches.
  • Auto-scale shared caches or use serverless caches for bursty workloads.

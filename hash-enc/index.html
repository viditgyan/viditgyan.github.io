🧭 Hashing Overview

Hashing maps variable-length input to fixed-length output. Depending on the algorithm, the goal may be speed, uniform distribution, locality awareness, or resistance to adversarial attacks.

Why Hashing Matters

  • 📦 Partitioning & Routing: Evenly map workload (Kafka, Cassandra).
  • 🔒 Security: Guarantee integrity, store passwords safely.
  • 🧭 Locality Preservation: Rolling/SimHash keeps similar items nearby.
  • ♻️ Compression & Dedup: Chunk fingerprints in backup systems.
  • ⚡ Performance: Constant-time lookups in hash tables, bloom filters.

Hash Function Families

Non-cryptographic Cryptographic Rolling Consistent Order-aware

Pick the function that matches your requirements—there is no universal choice.

Hash Output Anatomy

  • Bit-length: Determines collision risk (32-bit vs 128-bit vs 256-bit).
  • Endianness: Some libraries expose little-endian outputs (Kafka uses big-endian Murmur).
  • Seeding: Adjustable seed defends against hash-flooding attacks.
  • Streaming: Many hashes accept incremental updates for large payloads.

🔒 Encryption Techniques in Practice

Encryption algorithms come in symmetric, asymmetric and hybrid forms. Modern deployments favour authenticated encryption (AEAD) so confidentiality and integrity are handled together.

AES-GCM

AEAD Hardware Accelerated
  • 🛜 TLS 1.3 & HTTP/2: Default cipher suites in browsers and servers.
  • ☁️ Cloud KMS: AWS KMS, Azure Key Vault, GCP CMEK encrypt data keys with AES-GCM.
  • ⚙️ Why choose: Widely audited, hardware acceleration via AES-NI.

ChaCha20-Poly1305

AEAD SIMD Friendly
  • 📶 QUIC/HTTP3: Google Chrome, Cloudflare and Firefox use it for mobile clients without AES-NI.
  • 🔐 WireGuard: VPN protocol standardises on ChaCha20-Poly1305.
  • ⚙️ Why choose: Constant-time, performs well on ARM and embedded CPUs.

AES-XTS

Data at Rest
  • 💾 Disk Encryption: Microsoft BitLocker, Apple FileVault and Linux LUKS default to AES-XTS.
  • ⚙️ Why choose: Handles block devices, resists copy-paste block attacks.

X25519 (ECDH)

Key Exchange
  • 🔑 TLS 1.3: Mandatory-to-implement key agreement in RFC 8446.
  • 🕶️ Signal Protocol: Secure messaging (WhatsApp, Signal) uses X25519 for double ratchet initial keys.
  • ⚙️ Why choose: Fast, small keys, safe Montgomery ladder implementation.

Ed25519 (Digital Signatures)

Authentication
  • 🧾 OpenSSH: Default host/user key since OpenSSH 7.0.
  • 📦 Software signing: Used by the age file-encryption tool and the TUF update framework.
  • ⚙️ Why choose: Deterministic signatures, resistant to timing attacks.

RSA-OAEP & RSA-PSS

Legacy Compatible
  • 🏦 Hardware security modules: Broad support for 2048/3072-bit RSA keys.
  • 📄 Code signing: Windows Authenticode and Java JAR signatures remain RSA-based.
  • ⚠️ Note: Prefer OAEP for encryption and PSS for signatures; rotate to elliptic-curve when possible.

Format-Preserving Encryption (FF1/FF3)

Tokenisation
  • 💳 Payments: Card networks (e.g., Visa Token Service) use NIST SP 800-38G algorithms to keep PAN length.
  • 🗃️ Databases: Allows encrypting columns without schema changes.

Preparing for Post-Quantum

Hybrid
  • 🔐 Kyber + X25519: Chrome and Cloudflare test hybrid key exchange (TLS 1.3 draft) combining Kyber with classical curves.
  • 🗂️ NIST Round 3: Track Kyber (KEM) and Dilithium (signature) for future roll-outs.

⚖️ Hashing vs Encryption

Hashing is a one-way transformation that produces a fixed-length fingerprint. Encryption is reversible with the correct key and is used to keep data confidential. They solve different problems and are often combined (e.g., encrypt data, hash the ciphertext for integrity).

One-Way vs Two-Way

  • 🔁 Hashing: Deterministic, non-reversible. Collision resistance matters.
  • 🔐 Encryption: Reversible with keys. Security depends on key secrecy and algorithm strength.

Integrity vs Confidentiality

  • ✔️ Hashes verify integrity (e.g., container image digests).
  • 🕵️ Encryption keeps data confidential (e.g., TLS, disk encryption).
  • 🔗 Combine them with HMAC or AEAD modes for authenticated encryption.

Real-World Pairing

  • 📦 TLS 1.3: AES-GCM/ChaCha20-Poly1305 + HKDF (HMAC-SHA256) for key derivation.
  • 💳 Payment tokenisation: Format-preserving encryption for card numbers, hashes for lookup tables.
  • 🔐 Passwords: Hash (Argon2id) + encrypt storage vault with AES-GCM.

🔑 Encryption Fundamentals

Encryption transforms plaintext into ciphertext using keys. Understanding symmetric, asymmetric and hybrid approaches is essential before diving into specific algorithms.

Symmetric Encryption

  • 🧰 Single shared key: Same key encrypts and decrypts.
  • ⚡ Fast & scalable: Ideal for bulk data (storage, TLS record layer).
  • 🔐 Examples: AES, ChaCha20, legacy ciphers (3DES, RC4) now deprecated.

Asymmetric Encryption

  • 🔄 Key pairs: Public key encrypts or verifies; private key decrypts or signs.
  • 📬 Key exchange & signatures: RSA-OAEP, RSA-PSS, ECC (X25519, Ed25519).
  • ⚠️ Performance: Slower than symmetric; commonly used to bootstrap symmetric keys.

Hybrid Encryption

  • 🧪 Best of both: Use asymmetric algorithm to protect a randomly generated symmetric session key.
  • 🛡️ Real world: TLS, OpenPGP, envelope encryption in cloud KMS.
  • 🧭 Workflow: Generate data key → encrypt data with AES/ChaCha → encrypt data key with RSA/ECC → store both.

Key Size & Security Levels

  • 🔒 Symmetric: 128-bit minimum (AES-128) is standard; 256-bit for long-term archives.
  • 🗝️ RSA: 2048-bit baseline, 3072/4096-bit for long-lived certificates.
  • 🧮 ECC: 256-bit curves (secp256r1, Curve25519) roughly equal to 3072-bit RSA.

🔄 Modes, AEAD & Integrity

Choosing the right mode of operation prevents subtle vulnerabilities such as IV reuse or padding oracles.

AEAD (Authenticated Encryption)

  • 📦 AES-GCM, ChaCha20-Poly1305: Provide confidentiality + integrity in one operation.
  • 🧾 Additional data: Protect headers/metadata using Associated Data (AD) without encrypting it.
  • ⚠️ Nonce discipline: Never reuse nonce/IV for the same key.

Stream & Counter Modes

  • ⚙️ CTR, ChaCha20: Generate keystream, XOR with plaintext; parallelisable.
  • ❗ Integrity required: Pair with MAC/HMAC to avoid bit-flip attacks.

Legacy Block Modes

  • 🧊 CBC: Historically common; vulnerable without MAC (padding oracle).
  • 🔁 CFB/OFB: Turn block cipher into stream cipher; rarely used in new designs.
  • 🚫 ECB: Never use—reveals plaintext patterns.

Integrity Checks

  • 🛡️ HMAC-SHA256: Pair with encryption when AEAD unavailable.
  • 📥 Encrypt-then-MAC: Modern best practice (TLS 1.2+).
  • 📤 MAC-then-Encrypt: Deprecated due to oracle attacks.

🗝️ Key Management & Compliance

Robust encryption depends on how keys are generated, stored, rotated and audited.

Generation & Rotation

  • 🎲 Entropy: Use cryptographically secure RNGs; avoid manual passphrases.
  • 🔁 Rotation: Automate via KMIP/KMS policies; track key version in metadata.
  • 📅 Compliance: PCI DSS requires annual rotation or post-compromise rekey.

Storage & Access Control

  • 🔐 Hardware-backed: HSMs, Cloud KMS, TPM/TEE for high-assurance workloads.
  • 🔑 Envelope encryption: Protect data keys with master keys; master keys stay in HSM/KMS.
  • 🧾 Audit trails: Log every key access and admin action for compliance.

Secrets Distribution

  • 🚀 Service Mesh & MDM: Use Vault, AWS Secrets Manager, Azure Key Vault for dynamic secrets.
  • 🤝 Zero trust: Issue short-lived credentials bound to workload identity.
  • 🧭 Fallback plan: Document key recovery and incident response procedures.

Regulatory Alignment

  • 📜 GDPR & HIPAA: Require encryption in transit & at rest plus breach notification.
  • 💳 PCI DSS: Mandates strong cryptography, dual control for key custodians.
  • ⚙️ FIPS 140-3: Use validated modules when government or regulated sectors demand it.

🧪 Key Hash Properties

Uniformity

Outputs should cover the hash space evenly to minimise collisions and hotspots.

Measure: Chi-squared or avalanche tests (flip 1 input bit → ~50% output bits flip).

Determinism

Same input → same output, regardless of platform or language (unless purposely seeded).

Collision Resistance

Hard to find two inputs with same hash. Critical for security; relaxed for non-crypto scenarios if uniformity is strong.

Preimage Resistance

Given a hash value, infeasible to recover original message. Mandatory for secure storage and signatures.

Performance

Balanced trade-off of throughput (GB/s), latency (ns/byte) and CPU features (SIMD, hardware instructions).

Locality Sensitivity

Some hashes (SimHash, MinHash) intentionally keep similar inputs close together to enable near-duplicate detection.

⚡ High-Speed Non-Cryptographic Hashes

Optimised for speed, low-latency partitioning, in-memory data structures and deduplication where adversarial resistance is not the primary goal.

MurmurHash3

Kafka Cassandra

Designed by Austin Appleby for uniform distribution with strong avalanche behaviour.

// Kafka default partitioner (Java) int partition = Math.abs(MurmurHash3.murmur3_x86_32(keyBytes, 0, keyBytes.length, 0)) % numPartitions;
  • 🚚 Kafka: Default partitioner hashes record keys with Murmur3-32 (seed = 0) for stable routing.
  • 🗂️ Apache Cassandra & ScyllaDB: Murmur3Partitioner (64-bit) distributes tokens across the ring.
  • 🔐 Drawback: Non-cryptographic; randomise the seed or add SipHash when accepting untrusted keys.

xxHash

SIMD-Optimised Streaming

Ultra-fast hash designed by Yann Collet; xxHash3 reaches 30+ GB/s on modern CPUs via AVX2/AVX-512.

  • 📼 Zstandard & LZ4: Frame and block checksums use xxHash for high-throughput verification.
  • 🖥️ ClickHouse: xxHash64 powers hash partitioning and deduplication functions.
  • ⚙️ Tip: Prefer 64-bit or 128-bit variants to keep collision probability negligible.

FNV-1a

Portable RFC 3074

Fowler–Noll–Vo hash favoured for simplicity and predictable cross-language output.

  • 🌐 DHCP Load Balancing: IETF RFC 3074 specifies FNV-1a for consistent server selection.
  • 🧮 Development: Popular in simple hash-table utilities (e.g., Rust’s fnv crate) when repeatable output is required.
  • ⚠️ Security: Susceptible to hash-flooding; pair with a random seed or SipHash when inputs are attacker controlled.

CityHash / FarmHash

Google BigTable

Google’s high-speed family tuned for short strings. FarmHash dispatches to the best variant for the CPU at runtime.

  • 🧠 TensorFlow: tf.string_to_hash_bucket_fast uses FarmHash for deterministic sharding.
  • 📚 Google storage systems: The CityHash paper documents internal use for SSTable indexing.
  • ⚠️ Note: Non-cryptographic—prefer SipHash/HighwayHash when inputs may be adversarial.

🔁 Rolling & Locality-Sensitive Hashes

Ideal for sliding windows, deduplication, near-duplicate detection and streaming analytics.

Rabin-Karp Rolling Hash

Chunking Rsync

Maintains hash value while sliding over input, enabling O(1) updates.

  • 🗂️ Deduplication: Content-defined chunking in rsync, Dropbox, BorgBackup.
  • 📚 Search: Fast substring matching (e.g., plagiarism detection).

SimHash

Search Near-Duplicate

Converts high-dimensional vectors into compact fingerprints preserving cosine similarity.

  • 🔍 Google: Identify near-duplicate web pages.
  • 📰 News feeds: Deduplicate headlines/content in real time.

BuzHash

Streaming Byte-Oriented

Uses rotate-xor operations; ideal for streaming chunk boundaries without multiplication.

  • 💾 BorgBackup & restic: Content-defined chunking relies on BuzHash for deduplication.
  • 🔁 Firmware updates: Lightweight implementation suits embedded delta distribution.

MinHash

Set Similarity

Approximates Jaccard similarity using random permutations.

  • 📊 Apache Spark MLlib: MinHashLSH groups similar documents and events.
  • 🎧 Recommendation systems: Large platforms cluster users/items based on MinHash sketches.

🌐 Consistent & Rendezvous Hashing

Classic Consistent Hashing

Keys and nodes are plotted on a ring. Only a fraction of keys move when nodes join/leave.

  • 🗄️ Memcached: Twemproxy/Nginx upstream distribution.
  • 📘 Cassandra: Murmur3 partitioner + virtual nodes for load balancing.
  • 🛡️ Best Practice: Use virtual nodes to smooth uneven node capacity.

Rendezvous (Highest Random Weight)

Each node computes hash with key; highest score wins. Simple, optimal load distribution.

  • 🕸️ Akamai CDN: Original HRW algorithm balances edge caches.
  • ☁️ Ceph CRUSH: Uses a weighted rendezvous variant for placing objects on OSDs.

Jump Consistent Hash

Efficient (O(1)) mapping introduced by Google for sharding billions of keys.

// Jump consistent hash (Go) func jumpConsistentHash(key uint64, buckets int32) int32 { var b int64 = -1 var j int64 = 0 for j < int64(buckets) { b = j key = key*2862933555777941757 + 1 j = int64(float64(b+1) * (float64(1<<31) / float64((key>>33)+1))) } return int32(b) }

Documented in Google Cloud Bigtable; adopted by Redis/etcd client libraries that need predictable sharding without storing a ring.

🔐 Cryptographic Hash Families

Provide collision, preimage, and second-preimage resistance—mandatory for signatures, tamper detection, and zero-trust use cases.

SHA-256 / SHA-512 (SHA-2)

Blockchain TLS
  • ⛓️ Bitcoin: Double SHA-256 for block headers and transaction IDs.
  • 🔐 TLS: Certificate fingerprints, HMAC-SHA256 for message auth.

SHA-3 (Keccak)

NIST

Sponge construction; adjustable output length.

  • 🧪 Use: Post-quantum research, Ethereum (Keccak-256 variant).
  • ⚙️ Tip: Efficient on hardware (FPGA/ASIC) due to simple permutation core.

BLAKE2 / BLAKE3

Modern Alternative Streaming

BLAKE2 matches SHA-3 security with higher speed; BLAKE3 adds tree hashing for multicore scalability.

  • 🔐 libsodium & Argon2: BLAKE2b is the default general-purpose hash and key derivation primitive.
  • 🧾 b3sum utility: Official BLAKE3 tool delivers ultra-fast file integrity checks; adopted by backup and artifact pipelines that need multi-GB/s hashing.
  • 🚀 Performance: BLAKE3 scales with CPU cores (SIMD + threading) while keeping a small, constant-state.

HMAC

Integrity

Hash-based Message Authentication Code: combine hash with secret key.

  • 🔑 Use: AWS SigV4 (HMAC-SHA256), JWT HS256.
  • 🛡️ Note: Resistant to length-extension attacks when built on MD/SHA families.

🛡️ Password Hashing & Key Derivation

Argon2id

PHC Winner

Memory-hard, GPU-resistant. Configurable time, memory, parallelism parameters.

  • 🔐 Use: Modern password storage, API key derivation.
  • ⚙️ Guideline: Allocate ≥64MB memory, 2 iterations, parallelism = CPU cores.

bcrypt

Legacy

Still solid, but 72-byte password limit. Cost parameter controls CPU usage.

Move to Argon2id or scrypt when GPUs/ASIC resilience is required.

scrypt

Memory-Hard

Used by Tarsnap, Litecoin mining. Memory parameter defends against ASICs.

PBKDF2

RFC 8018

Widely supported but CPU-bound (easy for GPUs). Use high iteration counts and longer salts.

Salts & Peppers: Always store per-user random salt (≥128 bits). Optional pepper stored in HSM/KMS protects against database leaks.

🚀 Real-Time Production Scenarios

Kafka Partitioning (Murmur3)

  • Ensures stable partition selection for keyed events.
  • Seed = 0 for compatibility; custom partitioner can inject random seeds to rebalance.

Cassandra & Scylla Token Rings

  • Murmur3Partitioner hashes partition keys to 64-bit tokens assigned around the ring.
  • Virtual nodes spread token ownership so new nodes take balanced slices during expansion.

Git Content Addressing (SHA-1 → SHA-256)

  • Blob hashes store entire repo history; the identifier travels with every clone.
  • Optional SHA-256 mode shipped in Git 2.29 while SHA-1 remains default for backward compatibility.

Zstandard & LZ4 Checksums (xxHash)

  • Frame and block trailers carry xxHash fingerprints so decompression detects corruption at wire speed.
  • Backup and CDN pipelines relying on these codecs verify chunks with the embedded hashes before serving.

Blockchain & Smart Contracts

  • Ethereum uses Keccak-256 for address derivation, storage tries.
  • Solana leverages SHA-256 hardware acceleration (compute budget per transaction).

APIs & Auth (HMAC)

  • Stripe, Slack sign webhooks with HMAC-SHA256 and timestamp to prevent replay.
  • JWT HS256 tokens require rotated secrets and short TTLs.

Observability Pipelines

  • Logstash’s fingerprint filter uses Murmur3 or SHA-256 to deduplicate events before indexing.
  • Apache Spark MLlib MinHashLSH groups similar records for near-duplicate detection at scale.

🗜️ Hashing for Compression & Deduplication

Content-Defined Chunking

Use rolling hash (Rabin/BuzHash) to select chunk boundaries when fingerprint modulo pattern matches.

  • 💾 Backup Systems: Borg, Restic, ZFS dedup.
  • 🌐 CDNs: Byte-range caching, video chunk reuse.

Compression Guardrails

  • Run strong hash (SHA-256) after compression/encryption to detect bitrot.
  • Store chunk ID (hash) + size → identical chunks are reused across backups.
  • Use 160+ bit hashes to keep collision probability negligible for billions of chunks.

Integrity vs Compression

CRC32 is fast but weak; pairing CRC32C (hardware-accelerated) + SHA-256 balances speed and security.

Avoid relying on CRCs for adversarial integrity—they detect random errors, not malicious tampering.

🧱 Security Hardening & Best Practices

Salt Everything

Store random salts per credential to defeat rainbow tables. Combine with pepper stored in KMS/HSM.

Keyed Hashes

Use HMAC or KMAC where authenticity is required. Raw hash comparisons are vulnerable to length-extension and timing attacks.

Hash-Flooding Defense

Randomise seeds or use SipHash/HighwayHash for untrusted input in hash tables to prevent DoS.

Stretched Hashes

For file integrity, combine fast hash for dedup + cryptographic hash for verification (xxHash + BLAKE3).

Timing-Safe Comparison

Use constant-time comparison functions (crypto.subtle.timingSafeEqual, bcrypt.compare) to prevent timing leaks.

Key Rotation & Versioning

Store hash metadata: algorithm, cost parameters, salt, version. Supports migrations (bcrypt → Argon2).

✅ Deployment Checklist

Algorithm Selection

  • Define threat model (adversarial vs benign).
  • Benchmark with realistic data distributions.
  • Consider hardware support (SIMD, crypto extensions).

Operational Controls

  • Log hash versions and parameters.
  • Monitor collision rates, partition skew.
  • Test rehashing path for migrations (e.g., Murmur → xxHash).

Security Hygiene

  • Store salts & peppers separately.
  • Rotate HMAC/signing keys, enforce TTL.
  • Use TLS when transmitting hashes to prevent tampering.

🧰 Troubleshooting & Diagnostics

Hot Partition

Check key distribution; consider random salting or Rendezvous hashing.

Unexpected Collisions

Verify seeding, upgrade to wider hash, add secondary hash for tie-breaker.

Hash Upgrade Path

Store {algorithm, version}; compute new hash at read time and re-save to migrate gradually.

Slow Password Verification

Re-calibrate Argon2 parameters annually; ensure servers sized for peak auth load.

🎤 Interview Prep Quick Hits

Explain Murmur vs SHA-256

Murmur is non-crypto, faster, used for partitioning. SHA-256 is cryptographically strong, slower, used for integrity and security.

Consistent Hashing Scenario

Discuss how adding a node to the ring only remaps a portion of keys; mention virtual nodes and replication factor.

Salt vs Pepper

Salt is stored with hash to prevent rainbow tables; pepper is secret-wide, stored in secure storage to mitigate DB leaks.

Rolling Hash Example

Describe Rabin-Karp in rsync: chunk boundaries triggered when hash modulo mask equals pattern.

Hash Collisions & Mitigation

Use wider hashes, secondary checks, or store original data for final verification (content-addressable storage).

Compression + Hashing

Explain chunk fingerprinting with strong verification to avoid collision-induced data loss.
